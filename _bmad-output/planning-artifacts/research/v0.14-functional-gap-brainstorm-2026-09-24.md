# v0.14.0 Functional-Gap Brainstorm

- **Date:** 2026-09-24
- **Branch:** `release-0.14.0` (base: `c444891 chore(release): 0.13.0`)
- **Mode:** Autonomous. BMAD `bmad-brainstorming` techniques plus a strategic-analyst (Mary) evidence pass. No user facilitation.
- **Question:** What functionality does RoboScope still need for v0.14.0? The focus is on high value at small-to-medium size.
- **Excluded (already in flight this iteration):** dependency upgrade; running on RoboScope's own Python interpreter; importing an existing venv as an environment.
- **Constraints respected:** `non-goals-v1-lock.md` (N-1 through N-11 are not proposed); offline-only (no CDN or SaaS dependency; notifications only via the existing self-hosted webhooks).

---

## 1. Techniques used

| Technique | How it was applied |
|---|---|
| **First Principles** | Asked what a test-management tool must do for its core promise. The answer: *run the right tests, at the right time, with the right config, then let people get the results out.* Each step of that chain was checked against the code. |
| **Reverse Brainstorming / Anti-Solution** | Asked "how would a user be silently let down?" This led to features that have a UI and docs but no backend effect (schedules, environment variables, `max_retries`, `parallel`). |
| **"What would a power user miss" (Role Playing)** | Personas: CI engineer (export, badge, JUnit), test author (diff before publish, variables), team lead (scheduled nightly, report cleanup), admin (per-item delete, metrics). |
| **SCAMPER** | *Substitute*: apply retention per item instead of "delete all". *Combine*: schedules plus run templates. *Adapt*: rebot JUnit. *Modify*: webhook payload formats. *Put to other use*: `ExecutionRun.parallel` for pabot. *Eliminate*: inert columns. *Reverse*: a "run now" action on a schedule. |
| **Question Storming / Five Whys** | Why does a nightly schedule produce no runs? Because no APScheduler job reads `Schedule`. Why was it never noticed? The e2e tests only check the CRUD and cron-editor UI. |
| **Docs-vs-Code audit (Mary)** | The in-app docs (`frontend/src/docs/content/en.ts`) were grepped for promises and each promise was traced to code. Two promises are false today (see G-1, G-2). |

## 3. Analysis (Mary)

**The strongest signal is features that look shipped but do nothing.** G-1 (schedules) and G-2 (environment variables) each have a UI, a data model, e2e UI tests and in-app documentation promising the behaviour. A user who sets up a nightly schedule or a `BASE_URL` variable gets *silently nothing*. That is worse than a missing feature: it erodes trust in every other feature, and the docs currently state untruths in 4 locales. Both fixes are medium-sized because the hard parts already exist: APScheduler is running in `main.py`, `create_run` plus `dispatch_task` is the run path, and `_get_env_config()` in `tasks.py` is the obvious seam for env injection.

**The second cluster is roadmap items that are cheap because the data already exists.** G-13 (CSV/JSON export) is one endpoint over the existing `TestResult` rows, using stdlib `csv`. G-14 (single report delete) is a per-item extraction of `delete_all_reports`. G-20 (diff preview) is one GitPython call behind a new endpoint plus a `<details>` in `PublishModal`.

**Deliberately not shortlisted:**
- G-4 (run templates): valuable, but once G-1 lands, a schedule *is* a saved run config with a trigger. Revisit after measuring whether "Run now" on a paused schedule covers the need.
- G-6 (pabot): needs rebot merge and heal/quarantine listener interplay. Too big for this slice.
- G-7 (rerun-failed): medium-large, because rebot merge touches report parsing.
- G-18 (Prometheus): new dependency surface for a Phase-5 scale story.
- G-23 to G-25 (notifications): nice, but webhooks already cover the integration need.
- G-5 (`max_retries`) and G-6 (`parallel`): flagged instead as **inert columns to either wire up or hide**. A one-line note belongs in the next hardening pass.

**Guardrail for G-1:** the schedule trigger must **not** read `Schedule.advanced_config`/`Schedule.variables`. The trip-wire test `backend/tests/execution/test_schedule_trigger_gate_tripwire.py` pins that any reader must call `gate_advanced_execution`, which needs a request and user context that an unattended job does not have. Scheduled runs therefore carry only target, branch, env, runner and tags, which is exactly what the Schedule UI edits today.

## 4. Prioritized shortlist

| Rank | Idea | Value | Size | Why now |
|---|---|---|---|---|
| 1 | **G-1 + G-3**: schedules fire, plus "Run now" | Very high | M | A documented core feature that is dead today. Nightly regression is the #1 reason teams adopt a test-management tool. |
| 2 | **G-2**: environment variables with full CRUD plus injection into runs | Very high | M | The docs promise it, secrets encryption is already built, and the value is inert today. It unlocks `%{BASE_URL}`-style configs across envs (staging vs prod). |
| 3 | **G-13**: report test-results export CSV/JSON | High | S | Roadmap Phase 5, and people ask for it for spreadsheets and TMS handoff. One endpoint. |
| 4 | **G-14**: delete a single report | High | S | Missing CRUD piece. Today it is all-or-nothing and ADMIN-only. |
| 5 | **G-20**: per-file diff preview in the Publish modal | High | S-M | Committing blind is the main risk of a GUI git flow. The data is one `git diff` away. |
| 6 | G-4 saved run templates | Medium | M | Next iteration, after G-1 usage feedback. |
| 7 | G-15 JUnit export via rebot | Medium | S | CI interop. A good follow-up to G-13. |
| 8 | G-12 `%{ENV}` Flow-Editor awareness | Medium | S | Pairs with G-2 and is already specified. |
| 9 | G-26 repo-delete orphan cleanup | Medium | S | Hardening backlog. |
| 10 | G-5/G-6 inert columns: wire up or hide | Low | S | Honesty pass. |
